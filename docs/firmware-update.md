# KM003C firmware update protocol

This implementation follows the official POWER-Z Windows `Mtools.exe` v2.5.2
(SHA-256 `4c619023f98fb4b83e837ed1e27517a6dc48890eff9c4ca8d339f4f1febd1e73`),
downloaded through [ChargerLAB's support page](https://www.power-z.com/blogs/technical-support/power-z-km003c-km002c-technical-support).
The executable was inspected with REA and Ghidra 12.1.4. Addresses below refer
to that exact build. This is a reconstruction from shipped code; a physical
firmware flash has not yet been performed with this Rust implementation.

## Package

`FUN_140080110` reads a count and Qt `QString` metadata fields from the
`.mencrypt` file. `FUN_140080d20` also reads the following Qt `QByteArray`.
The observed KM003C V2.0.7 package has ten fields: file type, publisher,
format, model, version, date, CRC-32, plaintext size, Chinese notes and
English notes. The byte array contains AES-128-ECB ciphertext; the first
declared-size bytes decrypt to the firmware. Its CRC-32 matches the metadata.
The `km003c-lib::firmware` parser checks all of these before flashing.
The CRC covers the declared firmware bytes. The package's extra encrypted
block is passed to the bootloader unchanged; this analysis has not established
an independent host-side checksum for that block.

## Device selection and mode

`FUN_140013380` selects `UsbPolicyMX` for ChargerLAB vendor ID `0x5fc9`.
`FUN_14007b320` reads USB string descriptor index 2: it sends control command
`0x09` in `APP` mode to enter DFU and command `0x08` otherwise to run the
application. The CLI checks the target model in application mode before
switching to DFU.
The standard USB product name is separate. On a connected KM003C, descriptor
2 returned `APP` with NUL and erased padding, so the library trims that
padding before classifying the mode.

## DFU transfer

The `UsbPolicyMX` update method is `FUN_14007acd0`:

1. Send `Connect` (`0x02`) and expect `Accept` (`0x05`).
2. Send a 20 byte `Head` (`0x40`) status request with sixteen zero bytes.
   The returned `Head` packet has a zero status word at bytes 4–7.
3. Send `0x42` followed by a 64 byte setup record generated by
   `FUN_140079070`: start address `0x4000`, end address, plaintext size,
   CRC-32, model, version, date and a random word. Wait for `Accept` after
   the erase phase.
4. Send the original encrypted byte array in chunks of at most `0xff0`
   (4,080) bytes. Expect a `Sync` (`0x01`) reply for every chunk.
5. Expect `Finished` (`0x07`) after device verification. The CLI restarts
   the application if necessary and reads back its reported firmware version.

The Windows program's `FUN_14007d2d0` and `FUN_14007c9f0` handle raw USB
request/response transfers and the delayed erase reply. The Rust library
uses the existing `nusb` vendor interface transport with a short-packet
terminator, including a zero-length packet when needed.

## Validation

`firmware-update --verify-only` successfully parsed and CRC-checked the
official KM003C V2.0.7 package (SHA-256
`7a081af887fa8873d9e0cfc9cee9654187ab392f882efed16c1904a184ce8454`).
`firmware-update --check` also detected a connected KM003C in application
mode, confirmed its model, and read its current firmware version. `cargo check`
covers the library and CLI. The USB write sequence is based on static analysis
and has not yet been exercised on a physical device.
